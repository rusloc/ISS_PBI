| `public.analytical__air_sea_ports_codes` | `code` | `"name"` | ✓ | ✓ | ✓ |
| `portal.ports` | `port` | `country`, `region` (sea) | — | ✓ | ✓ |
| `portal.airports` | `airport` | `country`, `region` (air) | — | ✓ | ✓ |
| `public.analytical__sea_ports_regions` | `port_code` | `name` | ✓ | — | — |
| `portal.sla_master_coms` | `destination_port` | customs-clearance SLA days | — | ✓ | — |

There is no `dim_port`. The structural point: **port name and port country/region come from two
different table families with different key columns**, and nothing validates that the keyspaces
agree. `public.analytical__iss_country_mapping_codes` (`iso_2_char_code` → `country_name`) sits in
the same attribute block in all three files and is *not* a port table; `analytical__regions` is
organisational geography, unrelated.

Mechanics differ by report. COMS uses **no `join` for ports at all** — every attribute is a scalar
correlated subquery in `pre_calc` (EK 67-261, PO 415-609), all aliased `ports`, with a positional
sea+air `union all` where the mode is unknown. AVS uses real `left join`s
(`TRACKER CLIENT PROD MAIN.sql:189-196`) and joins `analytical__air_sea_ports_codes` **three times**
— `o` origin, `d` destination, `pa` discharge — plus `analytical__sea_ports_regions ps`.
